# Whitelists — инструменты проверки доступности российских сервисов в режиме "Белых списков"

Набор Python-скриптов для автоматической проверки доступности доменов и IP-адресов российских онлайн-сервисов во время включения операторами мобильной связи режима "Белые списки". Проект предназначен для формирования whitelist'ов, чтобы исключить важные сервисы из туннелирования и обеспечить их работу через прямое соединение.

## 📋 Возможности

### check-domains.py
Проверка доменов на доступность через HTTPS:
- ✅ Эмуляция браузера на Android (Chrome Mobile)
- ✅ Асинхронная проверка с настраиваемой параллельностью
- ✅ Проверка **всех** A/AAAA-адресов домена, а не одного
- ✅ Fallback на httpx при ошибках протокола
- ✅ Поддержка кастомных DNS-серверов
- ✅ Классификация ошибок (DNS, SSL, Timeout, HTTP, DPI, bot-block и др.)
- ✅ Детект подмены: страница-заглушка, редирект на оператора, подмена сертификата
- ✅ Чтение только начала ответа (не тянет мегабайты в мобильной сети)
- ✅ Выбор мобильного оператора для маркировки результатов

### check_pairs.py
Проверка пар (SNI, IP) — какие связки «домен + адрес» проходят в сети оператора:
- ✅ Резолв **всех** A/AAAA-записей домена, а не одного адреса
- ✅ Отдельная TLS-проба на каждый IP с SNI = домен
- ✅ Статусы PASS / DROP / RST / REFUSED / TLS_ERR / DNS_NX вместо «доступен/нет»
- ✅ Определение типа фильтрации: по IP, по SNI или по паре (контрольные пробы)
- ✅ Разбор сертификата (CN, fingerprint) как доказательство, что SNI обслужен
- ✅ Определение ECH (скрывает SNI от фильтра)
- ✅ Экспорт в JSONL и TSV + сводка

> Почему это важно: в режиме «белого списка» оператор фильтрует по паре
> SNI + IP. Один домен может быть разрешён частично — часть адресов проходит,
> часть нет. Проверка «домен доступен» по одному случайному IP даёт неверный вывод.

### build_all_release.py
Сборка release-списков по операторам из манифеста `configs/release.json`:
- ✅ Отдельный список на каждого оператора — фильтрация у них разная
- ✅ Учёт порога подтверждений между прогонами (`min` + `min_sources`)
- ✅ IP-список из тех же наблюдений, что и домены
- ✅ `--check` — сверка с тем, что лежит в `release/`, без записи файлов

## ✅ Актуальные данные

Списки собираются под конкретного оператора: фильтрация у них разная и меняется
во времени, поэтому общего «правильного» списка не существует.

| Оператор | Домены | IP-адреса (CIDR) |
|---|---|---|
| МегаФон | [`whitelist-megafon.txt`](https://raw.githubusercontent.com/kirilllavrov/whitelists/refs/heads/main/release/whitelist-megafon.txt) (351) | [`IP-whitelist-megafon.txt`](https://raw.githubusercontent.com/kirilllavrov/whitelists/refs/heads/main/release/IP-whitelist-megafon.txt) (360 сетей) |
| Ростелеком | [`whitelist-rostelecom.txt`](https://raw.githubusercontent.com/kirilllavrov/whitelists/refs/heads/main/release/whitelist-rostelecom.txt) (143) | [`IP-whitelist-rostelecom.txt`](https://raw.githubusercontent.com/kirilllavrov/whitelists/refs/heads/main/release/IP-whitelist-rostelecom.txt) (147 сетей) |

IP-список содержит только адреса доменов из соответствующего доменного списка —
он не заменяет его, а дополняет: при вердикте `ip` фильтр смотрит на адреса,
при `sni` — на имя в TLS.

## 🐧 Установка и использование на Linux

### 1. Скачивание репозитория

Клонируйте репозиторий:

```bash
git clone https://github.com/kirilllavrov/whitelists.git
cd whitelists
```

Или скачайте ZIP-архив и распакуйте:

```bash
wget https://github.com/kirilllavrov/whitelists/archive/refs/heads/main.zip
unzip main.zip
cd whitelists
```

### 2. Установка зависимостей

Создайте виртуальное окружение (рекомендуется):

```bash
python3 -m venv venv
source venv/bin/activate
```

Установите зависимости для check-domains.py:

```bash
pip install curl_cffi httpx aiodns aiohttp tqdm
```

### 3. Проверка доменов

Переходим в рабочую директорию:

```bash
cd tools
```

Базовая проверка (использует домены из ../src/domains/):

```bash
python3 check-domains.py
```

Проверка с настройками:

```bash
# Расширенный запуск со всеми параметрами
python3 check-domains.py ../src/domains \
    -c 10 \                                 # Количество параллельных запросов (по умолчанию 10)
    -q \                                    # Тихий режим (только прогресс, без деталей по каждому домену)
    -e category-gov-ru \                    # Исключить категорию (можно несколько: -e cat1 -e cat2)
    -e category-media-ru \                  # Исключить ещё одну категорию
    --dns 77.88.8.8 77.88.8.1 \             # Использовать кастомные DNS серверы (Яндекс DNS)
    --verify-ssl \                          # Включить проверку SSL сертификатов (по умолчанию выключено)
    --jitter 0.5 \                          # Случайная задержка между запросами в секундах (по умолчанию 0.1)
    --retries 3 \                           # Количество повторов при временных ошибках (по умолчанию 2)
    --no-impersonate \                      # Отключить эмуляцию браузера (только httpx)
    --no-http-fallback \                    # Отключить резервный HTTP (порт 80)
    --no-http3 \                            # Отключить HTTP/3 (по умолчанию включён)
    --show-config \                         # Показать текущую конфигурацию и выйти
    --show-fingerprints                     # Показать информацию об отпечатках curl_cffi
```

Тихий режим (без подробного вывода):

```bash
python3 check-domains.py -q
```

**После проверки:**

- Скрипт предложит выбрать мобильного оператора (1-6)

- Результат сохранится в `../build/domains_checked/whitelist-<TIMESTAMP>-<OPERATOR>.txt`

### 4. Сборка release

```bash
# Все операторы из configs/release.json
python3 tools/build_all_release.py

# Только один, и без записи — сверить с текущими файлами
python3 tools/build_all_release.py --only rostelecom --check
```

**Результат:** `release/whitelist-<оператор>.txt` и `release/IP-whitelist-<оператор>.txt`.
Если сборка ничего не изменила, файлы не перезаписываются содержимым-пустышкой:
оператор без источников останавливает сборку с ошибкой.

## 📊 Интерпретация результатов

### Статусы проверки доменов

|    Статус    |         Значение         |              Действие              |
|--------------|--------------------------|------------------------------------|
| ✅ OK        | Домен доступен (2xx/3xx) | Добавить в whitelist               |
| 🔐 SSL_ERR   | Ошибка SSL handshake     | Проверить вручную                  |
| 🕐 TIMEOUT   | Превышено время ожидания | Повторить позже                    |
| ❌ RST       | Соединение сброшено      | Возможно, блокировка               |
| 🌐 DNS_ERR   | Домен не резолвится      | Проверить DNS                      |
| ⚠️ HTTP_ERR  | Ошибка HTTP (4xx/5xx)    | Сервер работает, это НЕ блокировка |
| 🚫 UNREACH   | Хост недоступен          | Проверить маршрут                  |
| ❓ UNKNOWN   | Неизвестная ошибка       | Требуется анализ                   |

### check_pairs.py

Проверка пар (SNI, IP). Запускать **из мобильной сети оператора** (телефон в режиме
модема, роутер с USB-модемом, Android + Termux): с сервера или домашнего Wi-Fi
измеряется не белый список, а доступность из датацентра.

| Параметр | По умолчанию | Описание |
|------------|--------------|--------------------------------------|
| directory | ../src/domains | Директория с доменами |
| -c, --concurrency | 50 | Одновременных TLS-проб |
| --timeout | 3 | Таймаут одной пробы, сек |
| --port | 443 | Порт для TLS-пробы |
| --http-port | 80 | Порт HTTP-пробы, когда TLS не поднимается |
| --no-http-fallback | False | Не пробовать HTTP, если TLS не поднялся |
| --family | A AAAA | Какие записи проверять |
| --dns | системные | DNS-серверы для резолва всех адресов |
| -o, --operator | unknown | Оператор, в сети которого идёт проверка |
| --mcc-mnc | — | Код сети, например 250-01 |
| --channel | unknown | Канал измерения: mobile / wifi / unknown |
| --http | False | После TLS отправлять HEAD и писать HTTP-код |
| --no-control | False | Не выполнять контрольные пробы |
| --control-sample | 5 | Сколько пар проверять в контроле |
| --detect-egress | False | Определить внешний IP и провайдера перед прогоном |
| --dns-cache | из конфига | Кэш DNS (`cache_dns.py`): адреса берутся из него |
| --cache-only | False | Не обращаться к DNS вовсе, только кэш |
| --progress-bar | авто | Рисовать прогресс в одну строку (`\r`) |
| --no-progress-bar | авто | Печатать прогресс отдельными строками (для логов) |
| --repeat N | 1 | Повторять каждую пару N раз: показывает стабильность фильтрации |
| --no-ipv6 | False | Не проверять AAAA (когда IPv6 не выдаётся) |
| --ipv6-check | False | Проверить IPv6 и предупредить, если его нет |
| --out-dir | build/pairs | Каталог результатов |
| --format | both | Формат сырых данных: jsonl, tsv, both |
| --show-config | — | Показать конфигурацию и выйти |

**Хосты без TLS.** TCP и TLS пробуются раздельно, поэтому «SYN не дошёл»
(`DROP`) и «TLS не ответил» (`TLS_ERR`) различаются. Если TLS не поднялся,
проба повторяется обычным HTTP на порт 80 — иначе сайт, живущий только
по HTTP, неотличим от заблокированного. Успешная такая проба пишется со
статусом `PASS`, полями `transport: http`, `port: 80` и `tls_error`
с причиной отказа TLS: в отчётах видно, что это не TLS-проход.

Пример — госсайты, у которых нет TLS вовсе:

| Домен | :443 | :80 |
|---|---|---|
| `gov.ru`, `government.ru`, `kremlin.ru` | `TLS_ERR`, ответа нет | `200 OK`, реальные страницы |

**Тип фильтрации** определяется контрольными пробами:

| Вердикт | Значение |
|---|---|
| `ip` | разрешён адрес — проходит с любым SNI |
| `sni` | разрешено имя — проходит на любом адресе |
| `pair` | работает только конкретная пара SNI + IP |
| `both_shared` | проходит всё (ограничений в сети не видно) |
| `no_data` | ни одна пара не прошла |

**Формат наблюдений** (`build/pairs/pairs-*.tsv`):

```
domain  ip  family  sni  status  http  tls  cert_cn  ech  duration_ms  operator  mcc_mnc  channel  ts
```

### cache_dns.py

Сбор кэша DNS перед выездом в мобильную сеть:

```bash
python3 tools/cache_dns.py -o build/dns-cache.json
```

Зачем: в режиме «белого списка» DNS оператора не резолвит домены вне списка —
проверить их IP из мобильной сети невозможно, адрес просто неизвестен.
Кэш собирается заранее, пока есть обычный интернет, и `check_pairs.py`
использует его с `--cache-only`, не обращаясь к DNS оператора.

На практике это открывает домены, которые скрыты только на DNS: в первом
полевом прогоне `dbo-dengi.online`, `t-bank-app.ru` и `uralsib.ru` получили
`DNS_NX` у оператора, но прошли по IP через публичный DNS.

### build_release.py

Сборка итогового списка из результатов разных проверок:

```bash
python3 tools/build_release.py -o release/whitelist-x.txt --mode intersection \
    runs/megafon/2026-11-04-http.txt \
    runs/megafon/2026-11-04-tls.txt
```

`intersection` (по умолчанию) оставляет домены, подтверждённые **всеми**
источниками, `min --min-sources N` — не меньше N источников (удобно, когда
прогонов несколько и фильтрация нестабильна), `union` — объединение.
Понимает и txt-списки, и JSONL наблюдений; пишет отчёт с распределением
подтверждений.

IP-список строится из тех же наблюдений — отдельный сканер не нужен:

```bash
python3 tools/build_release.py -o release/whitelist-x.txt --mode min --min-sources 3 \
    runs/rostelecom/*.txt \
    --pairs runs/rostelecom/*.tsv \
    --ip-output release/IP-whitelist-x.txt
```

В `--ip-output` попадают только адреса итоговых доменов, схлопнутые в CIDR.
`--pairs` принимает и JSONL прогона, и `pairs.tsv` из отчёта (он в 10 раз меньше,
потому что содержит только прошедшие пробы). Источники доменов указывайте
**перед** `--pairs`: у флага `nargs='*'`, и он забирает все следующие аргументы.

### merge_runs.py

Агрегация нескольких прогонов — отделяет устойчивый результат от флапа:

```bash
python3 tools/merge_runs.py build/field-*\/pairs-*.jsonl -o build/merged
```

Результат: `stable-pass.txt` (проходят во всех прогонах), `flap-pass.txt`
(проходят не везде, с долей), `stable-blocked.txt` (не проходят ни разу),
`report.md`. Домен учитывается только в тех прогонах, где он проверялся,
поэтому короткие прогоны по подмножеству не искажают картину.

### pairs_report.py

Превращает наблюдения `check_pairs.py` в списки:

```bash
python3 tools/pairs_report.py build/field-*/pairs-*.jsonl -o build/report --domains-dir src/domains
```

Результат: `domains.txt` (домены с PASS), `ips.txt` (прошедшие адреса,
агрегированные в CIDR), `pairs.tsv` (только прошедшие пары), `report.md`
(сводка по статусам и категориям, включая частично доступные домены).

### lte_docker.sh

Полевые проверки из сети оператора **без потери связи на хосте**. Контейнер
получает собственный адрес в сети модема через `ipvlan` (или `macvlan`) и ходит
только через LTE, а маршруты, DNS и iptables хоста не меняются — Wi-Fi остаётся
для остальных задач.

```bash
# образ собирается заранее, пока есть обычный интернет
docker build -t whitelists-lte:latest tools/lte

tools/lte_docker.sh up                 # автоопределение модема (rndis_host)
tools/lte_docker.sh up enp3s0f3u2      # или явно
tools/lte_docker.sh check              # адреса, маршрут, DNS, доступность
tools/lte_docker.sh run Megafon 250-01 --repeat 3
tools/lte_docker.sh shell              # отладка внутри контейнера
tools/lte_docker.sh down               # убрать сеть
```

Почему `ipvlan`, а не bridged-сеть Docker: при `ipvlan l2` контейнер работает
с MAC хоста, поэтому модем (RNDIS) не отбрасывает пакеты. `macvlan` требует
второй MAC и на USB-модемах часто не работает; скрипт пробует `ipvlan` первым
и откатывается на `macvlan`, если первый не подошёл. Адрес контейнера
подбирается свободный: Docker по умолчанию может взять `.1`, занятый шлюзом.

DNS внутри контейнера — Docker-прокси `127.0.0.11`, который форвардит на DNS
оператора из сети модема, поэтому фильтрация имён измеряется корректно.

### field_test.sh

Автономный полевой прогон: запускается на ноутбуке с телефоном в режиме модема,
ничего не спрашивает и всё пишет на диск — работает, когда доступен только
белый список и внешней связи нет.

```bash
# оператор и код сети (MCC-MNC): МегаФон 250-01, МТС 250-02,
# Билайн 250-99, Tele2 250-20, Yota 250-11
bash tools/field_test.sh Megafon 250-01

# быстрый пробный прогон
LIMIT=50 HTTP_SUBSET=20 CIDR_LIMIT=20 bash tools/field_test.sh Megafon 250-01
```

Что делает по шагам:

| Шаг | Действие |
|---|---|
| 1 | показывает интерфейсы и маршрут, определяет канал (mobile/wifi) |
| 2 | проверяет внешний IP и провайдера — подтверждение, что мы в сети оператора |
| 3 | `check_pairs.py`: матрица SNI × IP по всем доменам через кэш DNS |
| 3a | `pairs_report.py`: списки доменов и IP, прошедших в сети оператора |
| 3b | прогон без кэша — фиксация того, что именно не отдаёт DNS оператора |
| 3c | состояние системного резолвера |
| 4 | `check-domains.py` по подмножеству — второе мнение по HTTP |

Перебор IP-сетей намеренно не выполняется: белый список состоит из конкретных
адресов сервисов, а не из диапазонов, поэтому адреса проверяются внутри
матрицы пар, а перебор 36k сетей ничего не даёт.

Прогресс виден в терминале: этап резолва, затем живая строка с процентом,
счётчиками статусов, скоростью и оценкой остатка. При записи в файл строки
печатаются раз в 2 секунды, чтобы журнал оставался читаемым.

Результаты: `build/field-<timestamp>/` — `field.log`, `pairs-*.jsonl`,
`pairs-*.tsv`, `summary-*.json`, `egress.json`, `report/` (домены, IP, сводка),
`dns-operator/` (что скрыл DNS оператора). В конце печатается краткая сводка и время прогона.

Переменные окружения: `LIMIT`, `HTTP_SUBSET`, `DNS_SAMPLE_PROBE`,
`PROBE_TIMEOUT`, `CONCURRENCY`, `REPEAT`, `DNS_CACHE`.

**Про нестабильность.** Фильтрация в режиме белого списка недетерминирована:
один и тот же домен на одном и том же IP проходит в одном прогоне и блокируется
в другом. В трёх прогонах подряд только 36 доменов из 364 прошли все три раза.
Для оценки устойчивости используйте `REPEAT=3` — инструмент считает `pass_count`
и `attempts` для каждой пары и помечает нестабильные (`unstable`) в отчёте.

### build_all_release.py

Настройки живут в `configs/release.json` — по блоку на оператора:

| Ключ | Описание |
|------|----------|
| `title` | Название оператора для вывода |
| `sources` | Маски файлов с доменами (`runs/<оператор>/*.txt`) |
| `pairs` | Маски выгрузок пар (`runs/<оператор>/*.tsv`) для IP-списка |
| `mode` | `intersection`, `union` или `min` |
| `min_sources` | Для `min`: в скольких источниках домен должен подтвердиться |

Чтобы добавить оператора, достаточно создать `runs/<оператор>/`, положить туда
`<дата>-http.txt` и `<дата>-tls.txt` (и `*.tsv` из отчёта), и дописать блок в манифест.

## 🔍 Примеры использования

### Сценарий 1: Проверка для конкретного оператора с кастомными DNS-серверами 

```bash
cd tools
python3 check-domains.py -c 15 --dns 77.88.8.8
# После проверки выберите оператора (например, 1 для Megafon)
# Результат: whitelist-01-01-2025-12-00-00-Megafon.txt
```

### Сценарий 2: Массовая проверка для всех операторов

```bash
# Повторите проверку для каждого оператора (меняя сеть/DNS)
# Затем соберите release по каждому:
python3 tools/build_all_release.py
# Получите whitelist-<оператор>.txt и IP-whitelist-<оператор>.txt
```

### Сценарий 3: Проверка конкретных доменов

```bash
# Создайте файл со списком доменов
echo -e "yandex.ru\ngoogle.ru\nvk.com" > ../src/domains/custom-list

# Проверьте только этот файл
python3 check-domains.py ../src/domains -e category-bank-ru category-gov-ru
```

### Сценарий 5: Поиск белого списка из мобильной сети

Проверка должна идти **через SIM-карту оператора** — телефон в режиме модема,
роутер с USB-модемом или Android + Termux. Иначе измеряется доступность
из датацентра, а не белый список.

```bash
cd tools

# 1. Убедиться, что трафик идёт через мобильную сеть (IP должен быть оператора)
python3 check_pairs.py --detect-egress -o Megafon --mcc-mnc 250-01 --channel mobile

# 2. Полный прогон: все A/AAAA, контроль типа фильтрации, JSONL + TSV
python3 check_pairs.py -c 50 --timeout 3 --http \
    -o Megafon --mcc-mnc 250-01 --channel mobile

# Результаты: build/pairs/pairs-<ts>.jsonl, pairs-<ts>.tsv, summary-<ts>.json
```

Что показывает результат:
- `PASS` — пара (SNI, IP) проходит, сервис работает в режиме ограничений;
- `DROP` — SYN не дошёл (типичная блокировка в белом списке);
- `RST` — соединение сброшено (DPI);
- вердикт в `summary.json` говорит, фильтруют по IP, по SNI или по паре.

Если вердикт `ip` — фильтр смотрит на адрес, и в `release/IP-whitelist-<оператор>.txt`
достаточно сетей. Если `sni` — наоборот, важны домены. Если `pair` — нужны обе
сущности вместе, и списки собираются согласованно (`build_release.py`
генерирует IP только для доменов, прошедших отбор).

## ❓ FAQ

**Q: Почему некоторые домены показывают HTTP_ERR?**  
A: Это означает, что сервер ответил с ошибкой (4xx/5xx). Домен доступен, это НЕ блокировка. Такие домены можно включать в whitelist.

**Q: Как увеличить скорость проверки?**  
A: Увеличьте параметр `-c` для доменов (но не более 20-30) или `NUM_THREADS` для IP. Будьте осторожны: слишком высокие значения могут вызвать блокировку со стороны серверов.

**Q: Можно ли использовать системные DNS?**  
A: Да, не указывайте параметр `--dns`. Для принудительного использования системных DNS убедитесь, что они корректно настроены в ОС.

**Q: Где найти итоговый whitelist?**  
A: В `release/` — по файлу на оператора: `whitelist-<оператор>.txt` и `IP-whitelist-<оператор>.txt`.
Общего списка «для всех» нет: операторы фильтруют по-разному.

**Q: Почему у операторов разные списки?**  
A: Фильтрация идёт по паре SNI + IP и отличается не только между операторами,
но и между базовыми станциями одного оператора. Пересечение всех операторов
дало бы список, неверный для каждого из них.

## 🤝 Вклад в проект

Мы стремимся создать максимально полный и точный whitelist российских сервисов, доступных через разных мобильных операторов. Поскольку доступность доменов может отличаться в зависимости от провайдера и региона, **нам важна ваша помощь!**

### Как вы можете помочь:

1. **Запустите проверку доменов** для вашего мобильного оператора (инструкции выше)
2. **Отправьте нам результат** — файл `whitelist-<TIMESTAMP>-<OPERATOR>.txt` из директории `build/domains_checked/`
3. **Создайте Issue** в репозитории с прикреплённым файлом или отправьте его любым удобным способом

### Почему это важно:

- ✅ Чем больше проверок от разных операторов — тем точнее итоговый whitelist
- ✅ Мы сможем выявить домены, доступные только у конкретных провайдеров
- ✅ Объединённые данные позволят создать универсальный список для всех пользователей
- ✅ Вы поможете тысячам людей настроить корректную работу российских сервисов

### Что мы делаем с полученными данными:

1. Собираем все файлы `whitelist-*-<OPERATOR>.txt` от сообщества
2. Кладём наблюдения в `runs/<оператор>/` — они и есть исходные данные release
3. `build_all_release.py` собирает `release/whitelist-<оператор>.txt` и IP-список к нему
4. GitHub Actions пересобирает release при изменении `runs/` и раз в неделю

**Каждый присланный файл делает общий whitelist лучше! 🙏**

Альтернативно, вы можете:
- Предложить новые домены для проверки через Pull Request в `src/domains/`
- Сообщить об ошибках в работе скриптов через Issues
- Улучшить документацию или добавить новые функции
