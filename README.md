# Whitelists — инструменты проверки доступности российских сервисов в режиме "Белых списков"

Набор Python-скриптов для автоматической проверки доступности доменов и IP-адресов российских онлайн-сервисов во время включения операторами мобильной связи режима "Белые списки". Проект предназначен для формирования whitelist'ов, чтобы исключить важные сервисы из туннелирования и обеспечить их работу через прямое соединение.

## 📋 Возможности

### check.py

Одна команда для проверки доменов в сети оператора:

- ✅ Спросит оператора и предупредит, если трафик идёт не через мобильную сеть
- ✅ Матрица пар SNI × IP, HTTP-проверка вторым мнением
- ✅ Сам кладёт наблюдения в `runs/<оператор>/<фаза>/` и пересобирает release
- ✅ Полный журнал прогона на диск — работает без терминала и внешней связи

```bash
python3 tools/check.py
```

Отдельные инструменты, из которых собран скрипт: они пригодятся для
ручных экспериментов.

### check-domains.py

Проверка доменов на доступность через HTTPS:

- ✅ Эмуляция браузера на Android (Chrome Mobile)
- ✅ Асинхронная проверка с настраиваемой параллельностью
- ✅ Проверка **всех** A/AAAA-адресов: каждая проба привязана к своему адресу,
  SNI и Host остаются доменом
- ✅ Fallback на httpx при ошибках протокола
- ✅ Поддержка кастомных DNS-серверов
- ✅ Классификация ошибок (DNS, SSL, Timeout, HTTP, DPI, bot-block и др.)
- ✅ Детект подмены: страница-заглушка, редирект на оператора, подмена сертификата
  (проверяется и на основном шаге с эмуляцией браузера)
- ✅ Чтение только начала ответа (не тянет мегабайты в мобильной сети)
- ✅ Выбор мобильного оператора для маркировки результатов

### check_pairs.py

Проверка пар (SNI, IP) — какие связки «домен + адрес» проходят в сети оператора:

- ✅ Резолв **всех** A/AAAA-записей домена, а не одного адреса
- ✅ Отдельная TLS-проба на каждый IP с SNI = домен
- ✅ Статусы PASS / DROP / RST / REFUSED / TLS_ERR / DNS_NX вместо «доступен/нет»
- ✅ Определение типа фильтрации: по IP, по SNI или по паре (контрольные пробы)
- ✅ AAAA-пробы отключаются сами, если IPv6 в сети не работает (`--ipv6-check`)
- ✅ Разбор сертификата (CN, fingerprint) как доказательство, что SNI обслужен
- ✅ Определение ECH (скрывает SNI от фильтра)
- ✅ Экспорт в JSONL и TSV + сводка

> Почему это важно: в режиме «белого списка» оператор фильтрует по паре
> SNI + IP. Один домен может быть разрешён частично — часть адресов проходит,
> часть нет. Проверка «домен доступен» по одному случайному IP даёт неверный вывод.

### build_all_release.py

Сборка release-списков по операторам из манифеста `configs/release.json`:

- ✅ Отдельный список на каждого оператора — фильтрация у них разная
- ✅ Учёт порога подтверждений между прогонами (`min` + `min_sources`)
- ✅ IP-список из тех же наблюдений, что и домены
- ✅ `--check` — сверка с тем, что лежит в `release/`, без записи файлов

```text
│   ├── check_pairs.py          # Проверка пар (SNI, IP) в сети оператора

│   ├── pairs_report.py         # Отчёт: домены и IP из наблюдений

│   ├── build_all_release.py    # Сборка release по всем операторам
│   ├── operators.py            # Одно имя оператора: манифест, runs/, наблюдения
│   └── cell_watch.py           # Монитор соты через adb (EARFCN, RSRP)
├── src/
│   └── domains/                # Списки доменов по категориям

├── runs/                       # Ваши прогоны; локально, в git не попадает
│   └── <оператор>/             # <дата>-http.txt, <дата>-tls.txt, <дата>-tls.tsv
├── configs/
│   ├── release.json            # Манифест: из чего собирать каждый release
│   ├── dns-cache.json          # Адреса всех доменов; обновляется workflow
│   ├── check-domains.json      # Основной конфиг для check-domains.py
│   └── check_pairs.json        # Конфиг для check_pairs.py
├── build/                      # Черновики прогонов (создаётся автоматически)
│   ├── domains_checked/        # Whitelist'ы по операторам
│   └── pairs/                  # Сырые наблюдения по парам SNI + IP (JSONL/TSV)
└── release/                    # Результат ваших прогонов

    └── IP-whitelist-<оператор>.txt # Адреса этих же доменов (/32 и /128)
```

## 🧭 Что на выходе

Инструмент не поставляет готовых списков: доступность зависит от оператора,
региона, базовой станции и момента времени, поэтому чужие результаты вам всё
равно не подойдут. Вы запускаете проверку в своей сети и получаете свои:

- `release/whitelist-<оператор>.txt` — домены, прошедшие проверку;
- `release/IP-whitelist-<оператор>.txt` — адреса этих доменов, по одной записи
  на адрес (`/32` для IPv4 и `/128` для IPv6);
- `build/run-<дата>/` — сырые наблюдения, из которых всё посчитано.

IP-список дополняет доменный, а не заменяет его: при вердикте `ip` фильтр
смотрит на адреса, при `sni` — на имя в TLS.

Файлы в `release/` этого репозитория — снимок с прогонов автора: они показывают
формат и масштаб, но к вашей сети отношения не имеют. Свой список вы получите,
запустив `check.py` у себя.

## 🐧 Установка и использование на Linux

### 1. Получение репозитория

Клонируйте репозиторий:

```bash
git clone https://github.com/kirilllavrov/whitelists.git
cd whitelists
```

Или скачайте ZIP-архив и распакуйте:

```bash
wget https://github.com/kirilllavrov/whitelists/archive/refs/heads/main.zip
unzip main.zip
cd whitelists
```

### 2. Установка зависимостей

Создайте виртуальное окружение (рекомендуется):

```bash
python3 -m venv venv
source venv/bin/activate
```

Установите зависимости:

```bash
pip install curl_cffi httpx aiodns aiohttp tqdm dnspython
```

### 3. Проверка доменов

```bash
python3 tools/check.py
```

Спросит оператора (1–10, Enter — не указывать) и сделает всё сам:

| Шаг | Что происходит |
| --- | --- |
| 1 | проверяет, что трафик идёт через мобильную сеть, и предупреждает, если нет |
| 2 | матрица пар SNI × IP по всем доменам из `src/domains/` |
| 3 | HTTP-проверка вторым мнением |
| 4 | наблюдения кладутся в `runs/<оператор>/<фаза>/` |
| 5 | release пересобирается: `release/whitelist-<оператор>.txt` и `IP-whitelist-<оператор>.txt` |

Полезные варианты:

```bash
python3 tools/check.py --limit 50     # первые 50 доменов — быстрая проба
python3 tools/check.py --repeat 3     # 3 повтора: видно стабильность фильтрации
python3 tools/check.py -o Megafon     # без вопроса об операторе
python3 tools/check.py --no-http      # только пары, без HTTP
python3 tools/check.py --no-release   # проверить, release не трогать
```

### Вручную, по шагам

Отдельные инструменты остаются доступны, если нужно вмешаться в середину:

```bash
python3 tools/check_pairs.py src/domains -o Megafon --channel mobile
python3 tools/pairs_report.py build/pairs/pairs-*.jsonl -o build/report
python3 tools/build_all_release.py --only megafon --check
```



принимает и прямые (`/`).

## 📊 Интерпретация результатов

### Статусы проверки доменов

| Статус | Значение | Действие |
| --- | --- | --- |
| ✅ OK | Домен доступен (2xx/3xx) | Добавить в whitelist |
| 🔐 SSL_ERR | Ошибка SSL handshake | Проверить вручную |
| 🕐 TIMEOUT | Превышено время ожидания | Повторить позже |
| ❌ RST | Соединение сброшено | Возможно, блокировка |
| 🌐 DNS_ERR | Домен не резолвится | Проверить DNS |
| ⚠️ HTTP_ERR | Ошибка HTTP (4xx/5xx) | Сервер работает, это НЕ блокировка |
| 🎭 SUSPECT_STUB | Заглушка вместо сервиса | Оператор подменяет ответ |
| ↪️ SUSPECT_REDIRECT | Редирект на оператора или блок-страницу | Оператор подменяет ответ |
| 🛡️ INTERCEPT_CERT | Сертификат не для домена, издатель неизвестен или оператор | Оператор вклинился в соединение |
| 🧾 SITE_CERT_MISMATCH | Сертификат от публичного УЦ на чужое имя | Ошибка сайта (парковка, чужой домен) |
| 🕳️ SUSPECT_EMPTY | Ответ 200 без тела | Ошибка сайта, проверить вручную |
| 🚫 UNREACH | Хост недоступен | Проверить маршрут |
| ❓ UNKNOWN | Неизвестная ошибка | Требуется анализ |

Статусы `SUSPECT_*` в whitelist не попадают, но означают разное. `SUSPECT_STUB`,
`SUSPECT_REDIRECT` и `INTERCEPT_CERT` — свидетельство того, что в соединение
вклинился оператор (это и есть фильтрация). `SITE_CERT_MISMATCH` и
`SUSPECT_EMPTY` — проблема самого сайта: сертификат выдан публичным УЦ на чужое
имя (парковка, перепутанный домен) или пустой ответ. Смешивать их нельзя:
в первом случае домена нет в белом списке, во втором оператор может быть ни при чём.
Классификация сертификата — эвристика по издателю (бренд оператора или пустой
издатель → подмена); издатель пишется в детали, чтобы сомнительное разобрать руками.

## ⚙️ Расширенные настройки

### Настройки check-domains.py

Настроить скрипт можно с помощью config/check-domains.json или аргументов:

| Параметр | Описание | Значение по умолчанию |
| ----------- | ------------- | ------------------ |
| directory | Путь к директории с доменами | ../src/domains |
| -c, --concurrency | Количество параллельных запросов | 5 |
| -q, --quiet | Тихий режим (только прогресс) | False |
| -e, --exclude | Исключить категорию (можно多次) | [] |
| --dns | Свои DNS серверы | системные DNS |
| --no-http3 | Отключить HTTP/3 (по умолчанию включён) | False |
| --verify-ssl | Проверять SSL сертификаты | False |
| --jitter | Случайная задержка (сек) | 0.1 |
| --retries | Количество повторов при ошибках | 2 |
| --no-impersonate | Отключить эмуляцию браузера | False |
| --http-fallback / --no-http-fallback | Резервная проверка по HTTP (порт 80) | выключено |
| --http3 / --no-http3 | HTTP/3 | выключено |
| --no-verify-cert | Не сверять сертификат с доменом | сверка включена |
| --no-stub-detect | Не искать признаки страницы-заглушки | поиск включён |
| `--limit N` | Проверить только первые N доменов | все |
| `--all-addresses` | Проверять все A/AAAA-адреса, даже если первый уже ответил | выключено |
| --operator NAME | Имя оператора без интерактивного ввода | — |
| --show-config | Показать конфигурацию и выйти | — |
| --show-fingerprints | Показать отпечатки и выйти | — |

### Настройки check_pairs.py

Проверка пар (SNI, IP). Запускать **из мобильной сети оператора** (телефон в режиме
модема, роутер с USB-модемом, Android + Termux): с сервера или домашнего Wi-Fi
измеряется не белый список, а доступность из датацентра.

| Параметр | По умолчанию | Описание |
| ------------ | -------------- | -------------------------------------- |
| directory | ../src/domains | Директория с доменами |
| -c, --concurrency | 50 | Одновременных TLS-проб |
| --timeout | 3 | Таймаут одной пробы, сек |
| --port | 443 | Порт для TLS-пробы |
| --http-port | 80 | Порт HTTP-пробы, когда TLS не поднимается |
| --no-http-fallback | False | Не пробовать HTTP, если TLS не поднялся |
| --family | A AAAA | Какие записи проверять |
| --dns | системные | DNS-серверы для резолва всех адресов |
| -o, --operator | unknown | Оператор, в сети которого идёт проверка |
| --mcc-mnc | — | Код сети, например 250-01 |
| --channel | unknown | Канал измерения: mobile / wifi / unknown |
| --http | False | После TLS отправлять HEAD и писать HTTP-код |
| --no-control | False | Не выполнять контрольные пробы |
| --control-sample | 5 | Сколько пар проверять в контроле |
| --detect-egress | False | Определить внешний IP и провайдера перед прогоном |
| --progress-bar | авто | Рисовать прогресс в одну строку (`\r`) |
| --no-progress-bar | авто | Печатать прогресс отдельными строками (для логов) |
| --repeat N | 1 | Повторять каждую пару N раз: показывает стабильность фильтрации |
| --no-ipv6 | False | Не проверять AAAA (когда IPv6 не выдаётся) |
| --ipv6-check | False | Проверить IPv6 и, если его нет, отключить AAAA-пробы |
| --dns-probe | False | Спросить DNS оператора по каждому домену (сигнал фильтра по именам) |
| --dns-probe-ns | системные | DNS-серверы для DNS-проб |
| --dns-probe-concurrency | min(concurrency, 8) | Одновременных DNS-проб (больше ретранслятор модема не держит) |

**Про DNS-пробы.** Кэш системного резолвера сбрасывается перед ними
(`resolvectl flush-caches`): иначе ответ, полученный до включения белого списка,
живёт в кэше и проба покажет «отвечает» там, где сеть уже не отдаёт имя.
Параллельность проб ниже, чем у TLS: 50 одновременных запросов перегружают
ретранслятор модема и дают таймауты, которые выглядят как фильтрация.
| --out-dir | build/pairs | Каталог результатов |
| --format | both | Формат сырых данных: jsonl, tsv, both |
| --show-config | — | Показать конфигурацию и выйти |

**Хосты без TLS.** TCP и TLS пробуются раздельно, поэтому «SYN не дошёл»
(`DROP`) и «TLS не ответил» (`TLS_ERR`) различаются. Если TLS не поднялся,
проба повторяется обычным HTTP на порт 80 — иначе сайт, живущий только
по HTTP, неотличим от заблокированного. Успешная такая проба пишется со
статусом `PASS`, полями `transport: http`, `port: 80` и `tls_error`
с причиной отказа TLS: в отчётах видно, что это не TLS-проход.

Пример — госсайты, у которых нет TLS вовсе:

| Домен | :443 | :80 |
| --- | --- | --- |
| `gov.ru`, `government.ru`, `kremlin.ru` | `TLS_ERR`, ответа нет | `200 OK`, реальные страницы |

**Тип фильтрации** определяется контрольными пробами:

| Вердикт | Значение |
| --- | --- |
| `ip` | разрешён адрес — проходит с любым SNI |
| `sni` | разрешено имя — проходит на любом адресе |
| `pair` | работает только конкретная пара SNI + IP |
| `both_shared` | проходит всё (ограничений в сети не видно) |
| `no_control` | контрольные пробы отключены (`--no-control`): тип не определить |
| `no_data` | ни одна пара не прошла |

**Формат наблюдений** (`build/pairs/pairs-*.tsv`):

```text
domain  ip  family  sni  status  http  tls  cert_cn  ech  duration_ms  operator  mcc_mnc  channel  ts
```

### build_release.py

Сборка итогового списка из результатов разных проверок:

```bash
python3 tools/build_release.py -o release/whitelist-x.txt --mode intersection \
    runs/<оператор>/on/*-http.txt \
    runs/<оператор>/on/*-tls.txt
```

`intersection` (по умолчанию) оставляет домены, подтверждённые **всеми**
источниками, `min --min-sources N` — не меньше N источников (удобно, когда
прогонов несколько и фильтрация нестабильна), `union` — объединение.
Понимает и txt-списки, и JSONL наблюдений; пишет отчёт с распределением
подтверждений.

IP-список строится из тех же наблюдений — отдельный сканер не нужен:

```bash
python3 tools/build_release.py -o release/whitelist-x.txt --mode min --min-sources 3 \
    runs/<оператор>/on/*.txt \
    --pairs runs/<оператор>/on/*.tsv \
    --ip-output release/IP-whitelist-x.txt
```

В `--ip-output` попадают только адреса итоговых доменов, по одной записи на
адрес: `/32` для IPv4 и `/128` для IPv6. Более широкая сеть не используется —
доступность проверена для конкретного адреса, и префикс разрешил бы соседние
адреса, которых в наблюдениях не было.
`--pairs` принимает и JSONL прогона, и `pairs.tsv` из отчёта (он в 10 раз меньше,
потому что содержит только прошедшие пробы). Источники доменов указывайте
**перед** `--pairs`: у флага `nargs='*'`, и он забирает все следующие аргументы.

### merge_runs.py

Агрегация нескольких прогонов — отделяет устойчивый результат от флапа:

```bash
python3 tools/merge_runs.py build/field-*\/pairs-*.jsonl -o build/merged
```

Результат: `stable-pass.txt` (проходят во всех прогонах), `flap-pass.txt`
(проходят не везде, с долей), `stable-blocked.txt` (не проходят ни разу),
`report.md`. Домен учитывается только в тех прогонах, где он проверялся,
поэтому короткие прогоны по подмножеству не искажают картину.

### pairs_report.py

Превращает наблюдения `check_pairs.py` в списки:

```bash
python3 tools/pairs_report.py build/field-*/pairs-*.jsonl -o build/report --domains-dir src/domains
```

Результат: `domains.txt` (домены с PASS), `ips.txt` (прошедшие адреса, по одной
записи на адрес — `/32` и `/128`), `pairs.tsv` (только прошедшие пары), `report.md`
(сводка по статусам и категориям, включая частично доступные домены).

### check.py — основной запуск и флаги

Один вход для обычной проверки — то, что нужно запускать в 95% случаев.

```bash
python3 tools/check.py                       # спросит оператора и сделает всё
python3 tools/check.py -o Megafon --phase on  # прогон в режиме белого списка
LIMIT=50 python3 tools/check.py              # быстрый пробный прогон

# три прогона подряд в одной фазе (базовая серия для сравнения)
for i in 1 2 3; do
    python3 tools/check.py -o Megafon --phase off --no-release
    sleep 60
done
```

Запускать имеет смысл только когда весь трафик хоста идёт через модем:
выключите Wi-Fi или оставьте модем единственным маршрутом по умолчанию.
Первым делом инструмент это проверяет и предупреждает, если меряет домашнюю
сеть вместо оператора.

| Флаг | По умолчанию | Описание |
| --- | --- | --- |
| `-o`, `--operator` | спросит | Оператор; попадает в имя файлов и в `runs/` |
| `--limit N` | 0 (все) | Проверить только первые N доменов — на обоих шагах |
| `--repeat N` | 1 | Повторов на каждую пару — видно стабильность фильтрации |
| `--timeout` | 3 | Таймаут одной пробы пары (SNI × IP), сек |
| `--http-timeout` | из `configs/check-domains.json` | Таймаут HTTP-запроса на шаге `check-domains`, сек |
| `-c`, `--concurrency` | 50 | Одновременных проб |
| `--dns` | системные | DNS-серверы для резолва (передаются и на HTTP-шаг) |
| `--no-cache` | — | Не брать адреса из `configs/dns-cache.json`, резолвить вживую |
| `--http-limit N` | 0 (все) | Сколько доменов проверять по HTTP |
| `--http-concurrency N` | 10 | Одновременных HTTP-проверок на шаге `check-domains` |
| `--no-http` | — | Только пары, без HTTP-проверки |
| `--no-release` | — | Проверить и записать наблюдения, release не трогать |
| `--phase off\|on` | unknown | Фаза сети: выключен или включён режим белого списка |

**Про нагрузку на канал.** Параллельность проб — не оптимизация, а условие
достоверности. На модеме после ~110 новых соединений при `-c 10` и выше
начинают теряться соединения **и к разрешённым адресам** (проверено: 35 %
провалов к Яндексу при `-c 50`). В результате домены из белого списка
выглядят заблокированными, и прогон показывает не фильтрацию, а предел
модема. При `-c 5` — 300 из 300 соединений без провалов, поэтому по умолчанию
`concurrency: 6`. Если результат «поплыл» — сравните статусы заведомо
разрешённых доменов (`yandex.ru`, `sberbank.ru`): если падают и они,
замер испорчен нагрузкой, а не фильтром.

**Про привязку к интерфейсу.** Если в системе несколько выходов (домашний Wi-Fi
и модем), маршрут по умолчанию уходит в тот, у которого меньше metric, и
измеряется чужая сеть. `--interface enp3s0f3u1u2` привязывает пробы, DNS и
запрос внешнего IP к нужному интерфейсу через `SO_BINDTODEVICE` — менять
маршруты не нужно.

**Про два таймаута.** `--timeout` — это одна TLS-попытка пары: при 3 с в мобильной
сети успевает уложиться даже медленный ответ. `--http-timeout` — весь HTTP-запрос
на шаге `check-domains` (коннект, TLS, ответ); он не наследуется от первого:
с 3 с живые сайты попали бы в `TIMEOUT`, а это уже влияет на `release/`. Если флаг
не задан, берётся `network.timeout_total` из `configs/check-domains.json`, и
действующее значение печатается перед шагом.

Что делает: проверка канала → пары SNI × IP → отчёт → HTTP-проверка →
`runs/<оператор>/<фаза>/<дата>-{tls.txt,tls.tsv,http.txt}` → пересборка release
для этого оператора. `runs/` — ваши наблюдения, в git они не попадают:
они нужны только чтобы собрать `release/` из нескольких прогонов.
Если оператора ещё нет в `configs/release.json`, он добавляется туда
автоматически (`min`, порог 2 источника).

**Фаза сети (`--phase off|on`).** Режим белого списка у оператора то включается,
то выключается, поэтому прогоны раскладываются по фазам:

- `off` — режим выключен: это базовый прогон, «как работает сеть без ограничений»;
- `on` — белый список включён: именно из этих прогонов собирается `release/`.

Разделение обязательно: если смешать фазы, в список разрешённого попадут домены,
которые проходили только потому, что ограничений не было. Поэтому манифест
смотрит только в `runs/<оператор>/on/`, а при `--phase off` release не собирается
(скрипт об этом сообщает). Флаг пишется в каждую запись наблюдений, так что
фазу видно и в `pairs.tsv`, и в отчёте.

**Канал и оператор проверяются сами.** `check.py` считает мобильным интерфейс,
который висит на USB (телефон-модем, HiLink-свисток вида `enp3s0f3u1u2`), и
отличает его от Wi-Fi/Ethernet. Оператор определяется по внешнему IP
(`ipinfo` → ASN): если выбран не тот оператор, в чьей сети идёт трафик, будет
предупреждение, а без `-o` — подставлен фактический.

Адреса берутся из `configs/dns-cache.json` — файла, который обновляет workflow
раз в неделю и при изменении `src/domains/`. Это не оптимизация: в сети
оператора DNS отвечает только на домены из белого списка, остальные
получают `DNS_NX`, и проверять у них нечего. Кэш собирается там, где
интернет обычный, и приносит адреса с собой. Собрать вручную:

```bash
python3 tools/cache_dns.py        # нужен dnspython: pip install dnspython
```

Если файла нет, прогон это скажет и продолжит с живым DNS. `--no-cache`
отключает кэш принудительно. Тот же кэш получает и HTTP-шаг (`check-domains.py
--dns-cache`): иначе в режиме белого списка он резолвит через DNS оператора и
на домены вне списка получает `DNS_ERR` — мерить становится нечего.

Результат прогона — `build/run-<дата>-<время>/`: `run.log` (полный журнал),
`pairs/` (сырые наблюдения), `report/` (домены, адреса, сводка).
Журнал пишется всегда, поэтому прогон можно оставить без терминала. Вывод
дочерних шагов идёт в журнал целиком — даже когда есть терминал.

Если ответ нужен без запуска пары — только `check-domains.py` с `-q`;
если без HTTP — `check.py --no-http`.

**Про нестабильность.** Фильтрация в режиме белого списка недетерминирована:
один и тот же домен на одном и том же IP проходит в одном прогоне и блокируется
в другом. В трёх прогонах подряд только 36 доменов из 364 прошли все три раза.
Для оценки устойчивости запускайте с `--repeat 3` — инструмент считает
`pass_count` и `attempts` для каждой пары и помечает нестабильные (`unstable`).

### build_all_release.py — сборка общего release

Настройки живут в `configs/release.json` — по блоку на оператора:

| Ключ | Описание |
| ------ | ---------- |
| `title` | Название оператора для вывода |
| `sources` | Маски файлов с доменами (`runs/<оператор>/on/*.txt`) |
| `pairs` | Маски выгрузок пар (`runs/<оператор>/on/*.tsv`) для IP-списка |
| `mode` | `intersection`, `union` или `min` |
| `min_sources` | Для `min`: в скольких источниках домен должен подтвердиться |

Чтобы добавить оператора, достаточно создать `runs/<оператор>/`, положить туда
`<дата>-http.txt` и `<дата>-tls.txt` (и `*.tsv` из отчёта), и дописать блок в манифест.

Поле `operator` в наблюдениях пишется руками, поэтому встречаются `Megafon`,
`ROSTELECOM`, `Ростелеком`. Ключ манифеста и каталог `runs/` — всегда слаг
(`megafon`, `rostelecom`), а имя из наблюдений приводится к нему при чтении
(`tools/operators.py`). Файлы прошлых прогонов не переписываются: в них остаётся
то, что было записано в момент проверки. Если наблюдение лежит не в своей папке,
`build_all_release.py` предупреждает: такой файл иначе молча подмешал бы домены
одного оператора в список другого.

## 🔍 Примеры использования

### Проверка в сети оператора

```bash
python3 tools/check.py
```

Всё остальное он сделает сам: спросит оператора, проверит пары и HTTP,
сохранит наблюдения в `runs/`, пересоберёт release.

### Быстрая проба

```bash
python3 tools/check.py --limit 50 --no-release
```

50 доменов, без записи в release — удобно, чтобы убедиться, что сеть та самая.

### Проверка конкретных доменов

```bash
mkdir -p /tmp/my-domains
printf "yandex.ru\nvk.com\n" > /tmp/my-domains/list
python3 tools/check-domains.py /tmp/my-domains -q --operator Megafon
```

### Свои DNS-серверы

```bash
python3 tools/check-domains.py src/domains -c 15 --dns 77.88.8.8 77.88.8.1
```

### Что показывает результат

- `PASS` — пара (SNI, IP) проходит, сервис работает в режиме ограничений;
- `DROP` — SYN не дошёл (типичная блокировка в белом списке);
- `RST` — соединение сброшено (DPI);
- `TLS_ERR` — TCP поднялся, но TLS не ответил (сервер без TLS или фильтр по имени);
- `DNS_NX` — адрес неизвестен: DNS оператора домен не отдал.

Вердикт в `summary.json` говорит, фильтруют по IP, по SNI или по паре.
Если вердикт `ip` — фильтр смотрит на адрес, и в `release/IP-whitelist-<оператор>.txt`
достаточно сетей. Если `sni` — наоборот, важны домены. Если `pair` — нужны обе
сущности вместе, и списки собираются согласованно (`build_release.py`
генерирует IP только для доменов, прошедших отбор).

## ❓ FAQ

**Q: Почему некоторые домены показывают HTTP_ERR?**  
A: Это означает, что сервер ответил с ошибкой (4xx/5xx). Домен доступен, это НЕ блокировка. Такие домены можно включать в whitelist.

**Q: Как увеличить скорость проверки?**  
A: Увеличьте параметр `-c` для доменов (но не более 20-30) или `NUM_THREADS` для IP. Будьте осторожны: слишком высокие значения могут вызвать блокировку со стороны серверов.

**Q: Можно ли использовать системные DNS?**  
A: Да, не указывайте параметр `--dns`. Для принудительного использования системных DNS убедитесь, что они корректно настроены в ОС.

**Q: Где найти итоговый whitelist?**  
A: В `release/` после прогона — по файлу на оператора: `whitelist-<оператор>.txt`
и `IP-whitelist-<оператор>.txt`. Готовых списков в проекте нет: они зависят от
вашей сети и вашего момента времени.

**Q: Почему у операторов разные списки?**  
A: Фильтрация идёт по паре SNI + IP и отличается не только между операторами,
но и между базовыми станциями одного оператора. Пересечение всех операторов
дало бы список, неверный для каждого из них.

## 🤝 Вклад в проект

Мы стремимся создать максимально полный и точный whitelist российских сервисов, доступных через разных мобильных операторов. Поскольку доступность доменов может отличаться в зависимости от провайдера и региона, **нам важна ваша помощь!**

### Как вы можете помочь

1. **Запустите проверку доменов** для вашего мобильного оператора (инструкции выше)
2. **Отправьте нам результат** — файл `whitelist-<TIMESTAMP>-<OPERATOR>.txt` из директории `build/domains_checked/`
3. **Создайте Issue** в репозитории с прикреплённым файлом или отправьте его любым удобным способом

### Почему это важно

- ✅ Чем больше проверок от разных операторов — тем точнее итоговый whitelist
- ✅ Мы сможем выявить домены, доступные только у конкретных провайдеров
- ✅ Объединённые данные позволят создать универсальный список для всех пользователей
- ✅ Вы поможете тысячам людей настроить корректную работу российских сервисов

### Что мы делаем с полученными данными

1. Собираем все файлы `whitelist-*-<OPERATOR>.txt` от сообщества
2. Кладём наблюдения в `runs/<оператор>/` — они и есть исходные данные release
3. `build_all_release.py` собирает `release/whitelist-<оператор>.txt` и IP-список к нему
4. GitHub Actions пересобирает release при изменении `runs/` и раз в неделю

### Каждый присланный файл делает общий whitelist лучше! 🙏

Альтернативно, вы можете:

- Предложить новые домены для проверки через Pull Request в `src/domains/`
- Сообщить об ошибках в работе скриптов через Issues
- Улучшить документацию или добавить новые функции
